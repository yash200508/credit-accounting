# Gas Station Credit Accounting

A Java 17 + JavaFX desktop application for managing gas-station/customer credit accounts in local offline mode. The current app uses a local SQLite database and keeps money values as integer paise for safer accounting calculations.

## Current repository state

- Application type: JavaFX desktop app packaged by Maven.
- Entry point: `com.gasstation.app.App`.
- Current database: local SQLite.
- Database path: `${user.home}/.credit-accounting/credit.db`.
- Main source tree: `src/main/java/com/gasstation/app`.
- Packaging scripts: `build-app-image.bat` and `build-installer.bat` for Windows app image/MSI packaging.
- No backend server or Android app is implemented yet.

## Local desktop setup

Prerequisites:

- Java 17+
- Maven 3.9+
- Windows packaging requires `jpackage` and the JavaFX runtime jars in `fx/`.

Common commands:

```bash
mvn test
mvn clean package
```

If Maven Central is blocked by the Codex/cloud environment proxy, dependency and plugin resolution can fail before compilation starts. In that case, retry in an environment with Maven Central access or a configured internal Maven mirror. See `docs/maven-build-troubleshooting.md` for safe mirror/cache guidance that does not commit secrets.

## Dependency-free smoke test

A small no-framework smoke test is available for core business logic and can run even before adding a full JUnit suite:

```bash
mkdir -p target/smoke-tests
javac -cp src/main/java -d target/smoke-tests src/test/java/com/gasstation/app/BusinessLogicSmokeTest.java
java -cp target/smoke-tests:src/main/java com.gasstation.app.BusinessLogicSmokeTest
```

This checks money parsing/formatting, interest calculation, KPI overdue/FIFO behavior, reminder placeholder rendering, transaction void-status behavior, DAO void-filter source checks, and import amount validation behavior.

## Known limitations

- The app is currently local/offline desktop only.
- There is no implemented role-based login yet.
- There is no REST backend, PostgreSQL production database, server deployment, or Android attendant app yet.
- Automated tests are still minimal and should be expanded before production use.
- Maven builds depend on external Maven repository availability unless dependencies are cached or mirrored; see `docs/maven-build-troubleshooting.md`.

## Future migration plan: desktop SQLite to backend PostgreSQL

Target architecture:

```text
JavaFX Admin/Desktop App -> Spring Boot REST API -> PostgreSQL
Android Attendant App    -> Spring Boot REST API -> PostgreSQL
```

### Current SQLite access points

DAO classes under `src/main/java/com/gasstation/app/dao` should be treated as the current persistence boundary:

- `CustomerDao`
- `TransactionDao`
- `SettingsDao`
- `ReminderDao`
- `AuditDao`

`Db` owns the SQLite connection and schema initialization.

### Current business logic candidates

Service classes under `src/main/java/com/gasstation/app/service` contain logic that should be preserved and gradually moved behind backend services where appropriate:

- KPI/risk and balance logic: `CustomerKpiService`
- Interest calculation: `InterestCalculator`
- Reminder templates: `ReminderTemplateService`
- Overdue policy: `OverduePolicyService`
- Export/report services: ledger, PDF, Excel services

### Migration sequence

1. Keep the JavaFX desktop app working in offline SQLite mode.
2. Define DTOs and API-client interfaces matching current DAO operations.
3. Add Spring Boot backend modules for auth, users/roles, customers, phone history, transactions, reminders, reports, settings, audit logs, and health checks.
4. Port schema to PostgreSQL with explicit migrations.
5. Add SQLite export and PostgreSQL import tooling for existing customer, transaction, reminder, setting, audit, and backup records.
6. Switch selected desktop screens from DAO calls to API-client calls behind feature flags.
7. Add offline queue/sync only after transaction conflict rules and audit rules are clear.
8. Keep SQLite read-only/archive mode during transition until production reconciliation is verified.
